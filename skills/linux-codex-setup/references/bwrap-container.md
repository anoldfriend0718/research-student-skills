# 容器内普通执行与只读保护

用于桌面已连接、但普通工具在bubblewrap启动阶段失败的情况。宿主CLI、工具审批后的执行及普通隔离执行是不同验收项。先保留当前工作实例和配置，不为诊断挂载账号目录或科研数据。

## 分层定位

1. **依赖：** 在实际桌面容器内检查PATH和已知捆绑位置。宿主有bwrap不代表桌面执行器能找到。安装须沿用用户授权，从已验证的发行版包源取得并保留包版本、摘要和签名检查依据；不要只修运行容器而遗漏持久镜像。
2. **命名空间与系统调用：** 依实际CLI帮助构造最小命令。案例主机的捆绑版本使用`codex sandbox --permission-profile :read-only -- COMMAND`，没有`linux`子命令；其他版本重新查帮助。若仍失败，在无网络、无账号挂载的诊断容器中追踪精确的调用、参数与errno，再比较seccomp规则。
3. **SELinux：** 用实际策略查询及可取得的AVC证据区分文件标签、进程域和filesystem类型。seccomp放行并不等于SELinux允许。不要把任意EACCES都推断为SELinux，也不要直接把audit2allow输出作为生产策略。

确需策略变更时限定于该桌面实例，保留现有rootless、MCS隔离和其他过滤。案例主机使用独立域，未修改通用container_t；继承当时基线的策略属于版本快照，宿主容器策略升级后需复核，不能当作通用模板复制。临时追踪所需的ptrace规则不得混入生产配置。用户不在sudoers时，继续重试sudo没有意义；管理员凭据由用户在服务器终端输入，不在聊天或脚本中收集。

## 正向和负向验收

至少同时验证：

- 普通只读命令真正启动并以0退出；记录实际执行环境。
- 外层容器可写的专用测试文件，在明确只读profile内部追加失败；外层独立回读确认内容未变。测试文件放在私有测试home内，不使用真实资料。
- `NoNewPrivs`、`Seccomp`及宿主SELinux状态仍符合设计。它们只是状态佐证，不能替代负向写入测试。

案例主机曾出现“命令退出0但只读文件仍可写”：跟踪显示请求已包含`--ro-bind / /`，XFS-backed home的只读bind remount被SELinux拒绝。给专用域补充所需filesystem remount权限后，写入才真正被拒绝。不能根据首次失败断言legacy CLI配置被忽略，也不能仅看`true`成功就宣布隔离修复完成。

旧Podman的同步`run --rm`客户端曾在容器结束后继续等待。诊断时可用有唯一名称的后台测试容器，分别读取容器状态、退出码和私有挂载目录中的日志；不要依赖广泛kill清理。

## 切换与原入口复验

先保存服务、镜像标识和安全配置，再停止旧桌面、启动新实例；同一持久home不能同时供两个应用实例使用。核对MCS标签和回退可访问性；同步systemd目标与preflight，避免下次启动旧版本或覆盖已验证策略。保留旧实例用于回退，核对实际running而非仅看oneshot服务active。

最后必须从原Dot任务入口执行普通工具，明确不进行审批重试。用独立通道生成未知随机标记，只告知路径，再比对Dot实际读值。此验收只证明该普通命令路径；宿主SSH、网络权限、模型请求和重启恢复分别记录，不能互相推导。发送Dot消息仍须遵守已有用户授权范围。

案例主机具体历史见[验证案例](centos8-case.md)。策略源码、哈希和回退脚本保存在用户私有设备记录，不放入通用技能作为自动安装器。
