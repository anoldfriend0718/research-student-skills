# CLI、网络与后台

## 只读基线

在已经核验身份的Linux主机运行`python3 /path/to/probe_linux.py`。需要检查已知服务时追加`--service mihomo.service`；不要猜测服务名并批量修改。JSON中缺少工具或inactive是诊断信息，不代表必须安装或启动。

同时核对有效SSH别名与目录权限，不打印完整SSH配置、环境变量或认证文件。工作目录不可写时检查所有者、失效链接及内容；不要递归chown科研目录。确需替换错误空目录，先完整改名保留，核验新目录归属和写入能力。

记录工具的实际解析路径，不只记录版本号。宿主的用户级CLI、桌面捆绑CLI和任务进程PATH可能不同；当前shell里`command -v codex`失败，不代表应用没有捆绑Codex。反之，宿主存在bwrap也不代表桌面任务能找到它。

glibc优先用`getconf GNU_LIBC_VERSION`或`os.confstr('CS_GNU_LIBC_VERSION')`读取运行时版本。案例主机曾被Python的`platform.libc_ver()`符号扫描误报为2.3.4，运行时实际为2.28；不能根据该启发式结果选择安装包或升级系统。非glibc系统无法返回该值时，另行核验其实际libc。

检查脚本中的代理变量只表示本次探测进程的环境：全部为false也不能证明包装脚本、后台或桌面没有代理。分别确认各执行入口，不打印完整环境。

## 安装与登录

1. 官方入口：[CLI安装](https://learn.chatgpt.com/docs/cli)与[认证](https://learn.chatgpt.com/docs/auth?surface=cli)。2026-11-01页面提供macOS/Linux独立安装器及其他安装途径；执行时重新确认来源和参数。新CentOS先完成[首次部署检查](new-centos.md)，不要假设已安装Python或Node。
2. 已有可用版本先查路径、包管理来源和配置。升级只在任务需要时进行，保留旧二进制/入口，避免覆盖PATH里另一个Codex。
3. 按实际架构和libc选择官方包；发行包校验应与可信发布元数据比对，自己算出的hash只能记录完整性，不能单独证明真实性。包下载失败可用官方替代分发来源，不关闭TLS或签名验证。
4. 用户级版本目录加入口便于回退；不要将案例主机的版本目录和包内路径当作通用安装规范。验证实际二进制和入口均返回正确版本。
5. 先看`codex login --help`。由用户完成官方认证；回调的localhost属于运行CLI/桌面的机器。无头机器只用当前版本支持的设备登录或必要的受控回调转发，不手工复制账号token。
6. `codex login status`如该版本支持，可核验认证状态；避免把可能包含敏感信息的原始输出直接交付。随后分别验证真实模型调用与普通隔离工具执行，两者通过才算完整CLI部署可用。

## 网络分层

按DNS→TCP/TLS→HTTP→账号/工作区→模型请求顺序诊断，每层只采集必要状态和耗时。

- 远端`127.0.0.1`指远端。通过SSH反向转发使用Windows代理仅是临时方案；客户端关闭会断开，不能满足独立运行目标。
- 先复用服务器既有出口。新代理仅在用户要求和授权范围内部署。Mihomo是案例主机采用的选择，并非所有Linux都必须安装的依赖。
- 代理端口和管理API默认只监听loopback；不复制原Windows配置中的LAN监听、TUN、透明代理或控制接口到服务器。代理节点凭据不得进入技能或日志。
- 若用户指定地区/节点，核对实际选择和规则，并实测出口；不要只改节点名称。系统代理、HTTP(S)_PROXY、桌面Chromium代理可能是不同路径。
- 用户级代理服务可使用`UMask=0077`、合理的失败重启；检查系统是否允许user service与linger。enable/linger只表示配置，不替代重启实测。未授权时不改系统级设置。
- 包装CLI时用已核验的绝对二进制路径并以`exec ... "$@"`转发参数，避免同名入口递归；设置必要的大/小写HTTP(S)_PROXY及NO_PROXY，不把含凭据地址写入通用脚本。
- 已运行后台进程不会自动继承新shell环境。定位本用户的具体后台及其管理方式，等待相关任务结束，按受支持命令重启/接管；不能广泛kill codex。验证只输出代理是否指向预期端点，不输出完整进程环境。

`curl`匿名接口401或网页403说明请求到达某HTTP服务，不说明登录/模型/工作区可用。工作区路由错误也不能直接归咎账号。收集错误类型、域名、状态码和耗时，去掉URL查询、认证头和用户内容。

## 后台与实际测试

先核对当前CLI帮助；不要默认每个版本都有`app-server daemon bootstrap`或`enable-remote-control`。仅在请求需要时启用远程控制，普通SSH终端不以此为前提。

使用已授权、可写的测试目录。下面只是命令形态，执行前核对当前`codex exec --help`及实际路径：

```bash
codex exec --skip-git-repo-check -s read-only -C "$test_dir" \
  'Reply exactly LINUX_CODEX_OK. Do not run commands or modify files.' </dev/null
```

记录真实输出及退出码，保护可能包含账户信息的日志。`</dev/null`明确非交互输入结束，避免等待SSH标准输入。此测试证明模型请求可用，不证明科研代码或工具权限可用。

再通过相同CLI入口做一次普通只读工具测试：执行无副作用命令并读出未知标记，独立核验实际工具输出；不能用提权重试的成功替代。按当前版本帮助选取权限参数，隔离初始化失败则继续检查bwrap、内核和实际限制。新主机验收要求见[分层验收](new-centos.md#分层验收)。

需要保留交互会话时，可使用tmux并向用户说明detach方法；tmux不能自然跨整机重启。桌面/后台可能各有独立会话，应分别测试用户实际入口，不只测试另起的CLI。

独立网络验收：核验服务器代理运行、包装入口和后台均指向服务器出口，在不影响其他会话的前提下停止本任务旧的客户端转发，再重复小请求。没有停止或隔离客户端依赖时，不称为独立验证。代理服务重启测试需避免打断正在执行的任务；科研主机整机重启不是默认验收项。
